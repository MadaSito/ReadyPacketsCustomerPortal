# Dropbox and Google Drive verification

The provider tests use local, synthetic protocol fakes only. No Dropbox or Google API was contacted, no real credential or cloud account was used, and no real browser/provider consent, native deployment, or TLS edge behavior is claimed.

- `scripts/dev/test.sh server/modules/storage/oauth/oauth.test.ts` passed 10 tests after the cloud egress runtime landed. Isolated MySQL covers encrypted grant and code storage, single-use state under concurrent callbacks, no exchange during the cross-site hop, single-use finish handles, absent and mismatched portal sessions, both expiry windows, stale versions, revocation, post-exchange reauthorization, fail-closed audit, malformed grants, local-first disconnect and uncertain remote revocation. The real HTTP pipeline covers CSRF, separate Lax binder, HEAD rejection, canonical host refusal without `Location`, no referrer, and query-free callback logging. Two Drive workers share one encrypted folder ID reservation. The real egress policy, with synthetic DNS and HTTPS handlers, tests disabled presets, public-IP enforcement, and Google Drive PUT-only `308` handling without following or returning `Location`.
- `scripts/dev/test.sh server/modules/storage/oauth/adapters.test.ts` passed 4 tests. Local protocol fakes exercise refresh, Dropbox stable paths, bounded upload sessions, checksums, source verification and write fences; Drive resumable ranges, write fences, provider URL origin/path locking, metadata verification and explicit deletion.

Before enabling production use, follow the [administrator API and registration guide](API.md) on the canonical deployment. Use a designated test account and non-sensitive test data for a manual provider acceptance test, including consent, transfer, disconnect and provider-side confirmation. No live-provider acceptance test was run for this increment.
