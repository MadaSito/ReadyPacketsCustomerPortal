# Authentication assurance verification

Server tests use isolated MySQL databases. `assurance.test.ts` runs the real assurance module with controlled Identity, audit, engagement and mail-readiness substitutes. `identity-integration.test.ts` combines the real Assurance and Identity modules and tRPC routers with controlled audit, mail, session transport and other external services. The component tests in `client/src/features/assurance/assurance.test.tsx` use jsdom and axe with test action adapters.

## Decisions for the architecture record

- **Enrollment and replacement**: Local accounts start with TOTP; after the account is fully authenticated, a user may enroll a user-verifying passkey. TOTP may be removed only if a passkey remains. Passkeys are a second factor here, not passwordless login; TOTP and recovery codes are not phishing-resistant.
- **Recovery acknowledgment**: Copying does not acknowledge. The exact batch identifier must match a durable pending batch, and old codes become invalid on regeneration. The browser’s temporary handoff is memory-only. Losing the pending batch requires a new authenticator app or passkey assertion, never an existing recovery code.
- **Credential administration**: Email mode invalidates the existing password material immediately and requires a verified address and ready selected mail route; a successful redemption is the password change. The two temporary modes require another change after MFA. An in-transaction audit failure blocks the write. A queued message is not evidence of delivery.
- **Locking and rotation**: Mutations recheck the current session and account under lock; paired user locks for admin changes are acquired in account order. Step-up password verification participates in the same transaction. Replacement transport tokens are issued after commit.
- **WebAuthn policy**: The configured canonical origin and its hostname are the trust anchors. The browser setting disables passkey registration in embedded preview; validate on the canonical HTTPS host. Signed counters may not regress; authenticators that consistently return zero can be used. The synthetic fixture is protocol evidence, not proof of platform or device compatibility.
