# Private files API

## Increment 04: workflow slots and audio

- **Requirement count (trusted Orders port):** `FilesModule.countFilesInSlot(orderId: number, slotKey: string, tx?: Tx, options?: { statusKey?: string }): Promise<number>`. Counts current, non-deleted, customer-visible originals only, never superseded versions or conversions. Pass the status key for workflow checks because keys may be reused by different statuses. For transition and upload admission, call in the same transaction after locking the order; numeric IDs are internal only.
- **Upload binding:** Existing multipart upload query accepts `slotKey?: string` and `statusKey?: string` as a pair. Slot keys follow `^[a-z][a-z0-9_]{1,47}$`; the status must match the current order status. For slotted uploads the Files module re-derives order authority, actor policy, the configured slot, and phase state before accepting bytes and again under the order lock. A replacement preserves its original slot and status.
- **Orders port consumed by Files:** `OrdersModule.getFileUploadSlots(principal: SessionPrincipal, orderPublicId: string, tx?: Tx): Promise<{ statusKey: string; slots: FileUploadSlot[] }>` returns current, unlocked slots writable by the current actor (read-only order/phase returns no writable slots). `FileUploadSlot = { key: string; label: string; kind: "document" | "audio"; maxCount: number; allowedTypes: readonly string[] }` where `allowedTypes` are canonical extensions without dots, empty means any Files-approved format of the specified kind. Files asks `OrdersModule.assertFileStatusWritable(principal: SessionPrincipal, orderPublicId: string, statusKey: string, tx?: Tx): Promise<void>` to apply phase policy to mutation of an already-admitted file. Orders checks pinned definitions; Files always checks the order-level lock and applies its own write rules.
- **File API extension:** Records add nullable `slotKey`, `derivedFromPublicId`, `conversionState: "converting" | "converted" | "failed" | null`, `conversionReason`, and `durationSeconds`. The authenticated order Files list adds `uploadSlots` and `audio` policy for authorized uploaders only. `files.admin.setAudioRules` is an audited step-up mutation for `platform.settings.manage`: `{ enabled: boolean; maxMinutes: number; bitrateKbps: number; keepOriginal: true }`. Originals remain retained by design; normal retention policy still applies.
- **Audio processing:** `files.audio_conversion` is a fenced job; it accepts a source file public ID, verifies the immutable original, stages in a private quarantine directory and reclassifies output as WebM audio before publishing a single linked derivative. `files.audio` reports binary availability when conversion is enabled; missing binary yields `AUDIO_CONVERSION_UNAVAILABLE`, without preventing an upload. Recordings stay on the device until an explicit upload. An optional transcript is supplied in a bounded multipart `transcript` field for a single audio file; it is encrypted and returned only under that file's normal access policy, never logged.
- **Public order files:** Files registers the `orderFiles` provider in `init()`. Only the scoped `files:read` service principal may query; bounded pages include current, non-deleted customer-visible metadata matching live order ownership. `updated_since` reflects immutable version creation time, not visibility edits. No file bytes, hashes, storage metadata, tickets, or transcripts are returned.
- **Operator guides:** See [Workflow uploads and audio administration](ADMIN_GUIDE.md) and [Upload files or record audio for an order](CUSTOMER_HELP.md).

## Provider interfaces

- `createObjectStorage({ config: { storageDir }, logger }): ObjectStorage`, as specified in `core/types.ts`. Keys are one of `files|staging|exports|backups|quarantine` followed by `/` and 32 lowercase hexadecimal digits. Only use `newKey(namespace)` to allocate keys. `get` accepts an optional inclusive range. Published objects are immutable; put and move must not intentionally overwrite an existing key.
- `FilesModule.revokeTicketsForOrder(orderId: number, tx?: Tx): Promise<void>` deletes all pending tickets for an internal order ID.
- `FilesModule.reassignOrderFiles(orderId: number, ownerUserId: number, tx: Tx): Promise<void>` updates the owner binding and invalidates tickets in the caller's order reassignment transaction.
- `FilesModule.assertCanReadFile(principal: SessionPrincipal, filePublicId: string, orderPublicId?: string): Promise<FileRecord>` checks current order and file visibility; an optional order binding is enforced.
- `FilesModule.enumerateOrderFiles(principal: SessionPrincipal, orderPublicId: string, options?: { cursor?: string; limit?: number; includeVersions?: boolean }): Promise<{ items: FileRecord[]; nextCursor: string | null }>` is a bounded collector API. It uses live order and visibility policy and returns no deleted files.
- `FilesModule.openForExport(principal: SessionPrincipal, filePublicId: string, orderPublicId: string, tx?: Tx): Promise<{ file: FileRecord; stream: Readable }>` reauthorizes each file under current order/visibility policy before opening the object. Pass the existing transaction when called in a fenced worker transaction. The caller must consume or destroy the returned stream (also if the outer transaction fails) and verify streamed bytes against the recorded size/hash when constructing or reconciling packages. Raw references or keys are never API inputs.
- `FilesModule.portableFiles(tx: Tx, { principal: SessionPrincipal; after?: string; limit: number; orderIds?: readonly number[] }): Promise<{ items: PortableStoredFile[]; nextCursor: string|null }>` checks portable export capability and verifies actual file owner against current order ownership in the supplied snapshot. Only active current versions are included. `PortableStoredFile = FileRecord & { storageKey: string; ownerPublicId: string; orderId: number; ownerUserId: number }`. Reauthorize before opening bytes.
- `FilesModule.backupFiles(tx: Tx, { after?: string; limit: number }): Promise<{ items: BackupStoredFile[]; nextCursor: string|null }>` is a trusted backup-worker traversal of all byte-bearing rows, including retained soft-deleted files and previous versions. `BackupStoredFile = FileRecord & { storageKey: string }`.
- `FilesModule.getOrderFileCopySource(filePublicId, tx)` is a trusted, fenced cloud-copy worker lookup. It locks current order/file scope, refuses held orders, inactive owners, deleted or purged data, and returns private source metadata, including the original status and slot, creation time, and current order name, for storage route resolution. Never send that metadata directly to a client or log it.
- `FilesModule.listOrderFileCopyMetadata(orderPublicId, filePublicIds, tx)` is a bounded transfer-view lookup for a caller that has already authorized the order. It exposes display name, captured status and slot, and metadata availability only, never private paths or bytes.
- The local publication transaction stages copy jobs for clean uploads and saved audio originals. The conversion worker stages a separate job for the scanned derivative, with the same status and slot. The local object remains authoritative. A later provider-transfer failure does not remove the local file.
- Upload requests may identify browser-saved audio through `source=recording`; the request then admits one supported audio file only. Customer file-picker availability and both upload authorization and commit consult `orders.gates.assertCustomerMayWork`; the in-transaction decision is authoritative, and refused work returns `ORDER_ACCEPTANCE_REQUIRED` (HTTP 409 before streaming).
- Non-imported uploads and audio conversion events correlate to their order and include visibility for order-history redaction. Uploads keep the existing `file.uploaded` event used by automation; `file_source` distinguishes saved recordings without exposing transcript text.
- `FilesModule.listOrderFileCopyCandidates(orderPublicId, tx)` is a bounded, locked traversal for the curated storage-copy automation action; held/read-only or inactive-owner orders are refused. `FilesModule.getUploadAutomationContext(filePublicId, dbOrTx)` exposes only the order/owner references and file category to the curated `file.uploaded` resolver, not names or bytes.
- `FilesModule.validatePortableObject({ stagedObject: StoredObjectInfo; displayName: string; category: FileCategory; contentType?: string }, tx?: Tx): Promise<{ extension: string; contentType: string }>` validates actual size/hash and classifies independently of sender-declared type, applying target file rules.
- `FilesModule.adoptVerifiedObject(input: AdoptVerifiedObjectInput, tx: Tx): Promise<FileRecord>` binds the caller-provided internal order/owner context created by the import and revalidates staged bytes against target policy before publishing. A trusted import caller must verify persisted actor/session authority and pass the checked admin principal with `portable.import` step-up to the same transaction. The target must have `origin=import`. The caller allocates a fresh `files` destination (do not populate) and owns outer rollback or fenced crash compensation. Input fields: `principal, publicId?, orderId, orderPublicId, ownerUserId, phasePublicId?, displayName, category, visibility, stagedObject, destinationKey, contentType?, createdAt?`. Adoption makes a new local version 1 for the single selected source version. Phase is represented by current `statusKey`; phase IDs for adoption must be absent or null. `createdAt` preserves the source timestamp when provided.
- `FileRecord` fields: `publicId, logicalPublicId, orderPublicId, phasePublicId, statusKey, displayName, category, visibility, size, sha256, contentType, extension, version, createdAt, supersededAt, deletedAt`. No tenant-local IDs, object keys, or ticket hashes leave the module's client-facing methods.

## HTTP and tRPC

- `POST /api/files/upload/:orderId` requires a full session and CSRF, accepts streaming multipart `files` fields. Set options via a strict query object (`category`, `visibility`, optional `versionOf`). Response lists individually committed and refused files in multipart order. Malformed or over-limit envelopes are refused before committing files.
- `POST /api/files/download` requires a full session and CSRF; send JSON `{ ticket }`. Tickets are never in URLs. Sends a private attachment; no Range on this endpoint.
- `trpc.files.list`, `.issueDownloadTicket`: full session and current resource authority. List returns effective upload policy only for actors with write access. Ticket TTL ≤60 seconds, hashed at rest, single use, and bound to the user, session and immutable file version. Issue and redeem check current persisted session state. Order locks restrict writes, not authorized reads.
- `trpc.files.setVisibility`, `.remove`, `.restore`: staff with the respective file capability and current write authority.
- `trpc.files.admin.get`, `.admin.setTypeRules`: admin. Rules can narrow the built-in format allowlist and limits; configuration cannot enable arbitrary formats. Changing rules rechecks the persisted administrator role, full session and fresh step-up inside the write transaction.

## Operations and policy

- Audit events: `file.uploaded`, `file.upload.denied`, `file.download.ticket_issued`, `file.download`, `file.download.result`, `file.export.open`, `file.visibility.changed` (attributes `from_visibility`, `to_visibility`), `file.removed` (a repeated delete records outcome `refused`, reason `ALREADY_REMOVED`), `file.access.denied` (security; object-level write refusals, recorded after rollback), `file.restored`, `file.rules.changed`, `file.imported`, `file.retention.purged`. File access records and the durable audit trail contain no display names, raw tickets, or private keys.
- Jobs: `files.retention` expires tickets and purges due soft-deleted files under a job fence and locked legal-hold check. It records durable intent before physical removal; completion and the row update share the fenced transaction. Stale upload staging is swept only in the uploader-owned partition, never portable/recovery staging. Settings key: `files.type_rules`.
- Health: `storage.local`, `files.antivirus`. Optional `createFilesModule(deps, { scanner })` injects a scanner for upload and adoption; the adapter must consume the entire stream to approve. Production composition leaves it unconfigured.
- UI: order Files tab and `/admin/files`. The Files tab uses server-supplied rules for early feedback and indeterminate progress until server confirmation. Tickets are requested per click, sent in a POST body, and never persisted in the query cache. Admin overview reports counts for byte-bearing versions and files in retention, not filesystem capacity.
