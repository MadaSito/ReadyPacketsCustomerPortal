# Trash Module (`server/modules/trash`)

Owner: `recovery_ops_engineer` (Increment 09, Decision D2 & D2.8).

## Responsibilities
- Participant registry (`TrashRegistry` / `TrashParticipant` in `./ports.ts`).
- Coordinator (`./service.ts`) orchestrating move-to-trash, restore, resumable fenced permanent deletion (`trash_purge_runs` + `trash_purge_run_targets`), per-order unreachable external storage-copy acknowledgment (`finishLeavingExternalCopies`), retention settings (`trash_retention_state` + `platform_settings` with `ownerWriteOnly: true`), and hourly retention clean-up (`trash.retention_cleanup`).
- tRPC router (`export const trashRouter` in `./router.ts`), mounted as `trash: trashRouter` in `server/trpc/root.ts`.

## Security & Concurrency Invariants (D2.8 v2)
1. **Canonical lock order**: `users -> sessions -> orders -> trash_purge_runs -> trash_purge_run_targets` (`actorGuard`, `jobAdmin.isDraining(tx)`, `maintenance.customerAccess(tx)`, and customer/order cascades).
2. **Fail-closed ports, drain gate & participants**: Missing `identity.trash`, `orders.trash`, `jobAdmin.isDraining(tx)`, `jobAdmin.maintenance.customerAccess(tx)`, or any participant in `EXPECTED_CONTAINER_PARTICIPANTS` refuses purge/cleanup with `503 UNAVAILABLE` before mutating or tombstoning.
3. **Permanent per-target run ownership (`trash_purge_run_targets`)**: Every purge claim inserts all expanded targets (root + every group addition including cross-owner reassigned additions + cascaded customer orders + the customer) into `trash_purge_run_targets` under `UNIQUE(entity_kind, entity_id)`. A target belongs to at most one purge run forever; overlapping standalone/root/customer purges fail closed with `409 PURGE_ALREADY_OWNED` while retries of the owning primary entity resume the same run. Normalized per-target checkpoints avoid run-level JSON size caps.
4. **Participant-effect MySQL advisory-lock fence**: Execution holds a dedicated-connection MySQL advisory lock (`GET_LOCK('rp.trash.<dbHash12>.run.<runRowId>', 0)`) across the entire run, verifies `IS_USED_LOCK(...) = CONNECTION_ID()` before every participant call, and pairs it with monotonic `fencingToken` CAS on every target checkpoint and Phase-3 tombstone write. Residual behavior: if a worker loses its MySQL TCP connection mid-participant step, MySQL releases `GET_LOCK` and a subsequent retry can enter that idempotent participant while the disconnected worker's in-flight step unwinds; the disconnected worker stops at its next `IS_USED_LOCK` / `fencingToken` check and cannot commit checkpoints or tombstones.
5. **Scoped per-order unreachable external-copy gate**: `finishLeavingExternalCopies` requires `trash.purge` + fresh step-up + mandatory `batchId` + server-checked typed `RP-...` order number for the specific failing target order (`targetOrderPublicId` inside a root/customer cascade run or the single order itself). Approval is persisted only on that target row in `trash_purge_run_targets`, never blankets sibling orders in a cascade, and is never set by retention sweeps.
6. **Mandatory `batchId` & durable post-claim idempotency**: Manual `restore`, `purge`, and `finishLeavingExternalCopies` require `batchId` on every item. `trash_idempotency_keys` reserves keys with `batchBindings` before any mutation; once a purge claim or mutation commits, the key/fingerprint is retained (storing `failed` or `completed` outcomes) and is only released when nothing was mutated.
7. **Retention CAS, `DELETE 0`, single-flight sweep & fair progression**: Enabling automatic clean-up or shortening an active retention period always requires step-up + exact `expectedVersion`, `reviewedDueCount`, and `DELETE <N>` confirmation (including `DELETE 0`). `runRetentionCleanup` enforces cross-process single-flight via `GET_LOCK('rp.trash.<dbHash12>.sweep', 0)`, rechecks `jobFence.assertStillOwned()` and transactional `isDraining(tx)` / `customerAccess(tx)` between targets, and advances a `(trashedAt, id)` cursor past legal-hold and backoff-Cooling (`nextRetryAt`) items so head-of-line failures never starve later due items.
