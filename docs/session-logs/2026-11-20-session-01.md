## Response and actions

1. Read both specifications and the brand guide in full; inspected the existing repository as reference.
2. Decision: clean rebuild in a new repository layout (`readypackets-portal`) on the specified stack
   (React 19, TypeScript, Tailwind, Vite, Node 22, Express 5, tRPC, Zod, MySQL 8, Drizzle), rather than
   patching the previous code, so documented source defects are not inherited.
3. Wrote the foundation: tooling, strict configuration validation, core contracts (dependency injection),
   procedure guards with capability + step-up enforcement, safe error mapping, request correlation context,
   field encryption baseline, isolated-database test helper, test fakes, client skeleton, route/feature
   registry, and the engineering build contract.
4. Divided the build among sixteen engineers by module (identity, assurance, HTTP security, platform, audit,
   SIEM, jobs/mail, orders, files, engagement, compliance, portable contract, portable operations,
   backup/deploy/CI, UI foundation, integrations) with the integrator owning composition, migrations,
   seed data, verification and documentation.

5. Ran independent security reviews of each module by a different engineer than its author, recorded the
   findings in `docs/security/REVIEW-*.md`, and remediated them. Recorded 21 architecture decisions in
   `docs/adr/`.
6. Produced one baseline migration (`migrations/0000_baseline.sql`) with a schema-contract test, a demo
   seed with synthetic data only, and a sandboxed preview build.
7. Tested the preview in a real browser as customer, staff and administrator on desktop and phone widths,
   and fixed what that found: navigation overflow, recovery-code wrapping, an input field the client added
   that strict server validation refused, audit attribute validation, step-up prompts on protected reads,
   avatar initials, console search on phones, order action labels and dialog cancel buttons, stale order
   detail after administrative changes, raw labels on the SIEM page, a sparse admin overview (five widgets
   added), widgets shown to roles without the capability, scheduler noise and anonymous session probes in
   the audit trail, and a client batch size larger than the server accepts.

## Response and actions (prompt 2)

1. Read the three documents and wrote `docs/engineering/INCREMENT_02_CONTRACT.md` and ADRs 0022 and 0023.
2. Offerings: the matrix became owner-controlled catalog data (`data/catalog/readypackets-offerings-v3.0.json`,
   schema-validated) loaded by an audited operator command, not code. Packets 1–6 × Basic / Standard /
   Premium are 18 products with outcome, timeline and deliverables. "Packet 7" is a bundle rule (15% when
   all six packets are in one order), computed on the server. Packet 8 is not loaded.
3. Orders: one tier per packet, quantity one, server-side quote, subtotal / discount / total stored on the
   order; packet picker in the order wizard; order detail and admin catalog show the new fields.
4. Production pipeline: manual P101 / P201 triggers on the console order page with the exact field set of
   the reference documents (the corrected P101 document wins: `order_scope_mode` is never sent), an
   encrypted outbox with retries, admin settings behind step-up, disabled until configured.
5. Independent security review of the webhooks by a second engineer found two high and five medium issues
   (receiver response text stored; interrupted dispatches could block re-send; lock order; destination
   could change under a queued dispatch; no order revalidation before sending; resend reason free text;
   export exclusion to be explicit). All were fixed and re-reviewed closed (PW-01 to PW-08).
6. Migration `0001_offerings_and_production_dispatch.sql` with backfill for existing rows and an upgrade test.
7. Browser pass found one integration defect: the bundled demo seed ran the catalog import entry point and
   exited before seeding accounts. Fixed by moving the shared mapper out of the command module, with a
   test that forbids one operator command importing another.
