## Response and actions

1. Added a native auto-installer for dedicated Ubuntu 26.04 LTS servers. It checks root custody of the checkout, can add a persistent 2 GB swap file, installs prerequisites and builds the reviewed local Git commit. It configures loopback MySQL 8.4 and serves the chosen host and optional redirect alias through Nginx. The names stay fixed after installation; certificate mode can change. Certbot is only installed for public TLS, with Ubuntu's `universe` enabled if needed. Repository access is needed for the clone or later fetch, not for the running portal.
2. Added local administrator bootstrap with a generated temporary password stored in `/root/readypackets-initial-admin.txt`. `Portal address`, `Sign-in name` and `Password` are shown once on the controlling terminal; without a terminal they are printed only with `--print-credentials`. Later runs refer to the saved file rather than showing the password again. First sign-in requires a new password and authenticator enrollment. The bundled offerings are loaded by default.
3. Updated the manual and automatic runbooks for the shared deployment lock, Nginx edge and TLS snippets, native upgrade and deactivation, and off-server copies of the backups and secrets.
4. Defined three `native-install` jobs on GitHub-hosted Ubuntu 26.04 runners: x64 self-signed without alias; arm64 self-signed with alias and `--swap yes`; and x64 local Pebble ACME on a runner prepared without `universe`, with renewal and certificate-mode switching. The workflow does not exercise native upgrade or uninstall or use the live Let's Encrypt service.

## Files

- `deploy/auto-install.sh`, `deploy/lib.sh`, `deploy/install.sh`, `deploy/upgrade.sh`, `deploy/uninstall.sh` and `deploy/nginx/*.conf.template`: automatic and manual host setup, site rendering, administrator bootstrap and lifecycle operations.
- `.github/workflows/native-install.yml`, `scripts/ci/native-install-{prepare,run,smoke}.sh`: runner preparation, installer checks and smoke checks.
- `docs/operations/AUTO_INSTALL.md`, `docs/operations/INSTALL.md`, `deploy/README.md` and `README.md`: deployment documentation; related updates in the changelog, SDLC, requirements register and application context.

## Results

- `native-install` passed in all three jobs for commit `1d60b9b` on 21 November 2026 ([run 44909497870](https://github.com/MadaSito/ReadyPacketsCustomerPortal/actions/runs/44909497870)); `ci`, `security` and `container` passed for the same commit. Observed on the runners: Ubuntu 26.04.1 LTS, Nginx 1.28.3, MySQL 8.4.13, Certbot 4.0.0; the installer itself took 38 to 51 seconds there.
- Getting to green took nine workflow iterations. Defects found and fixed on the way: `sudo` dropped the runner markers; the runner's `/opt` was world-writable with a default ACL (the installer's custody check refused it, as intended); Ubuntu 26.04's stock `nginx.conf` already sets `server_tokens` and other settings at http level, which made the site file a configuration error; a reload race let the packaged default page answer the installer's first probe; the smoke checks expected a dropped connection where Nginx answers `421` over HTTP/2.
- Two read-only reviews by team members were applied: a security review (custody of the clone, one lock, no shell tracing, password shown once, credentials out of command lines) and an operational review (challenge directory and umask with `--skip-dns-check`, loss of the saved password after two interrupted runs, Certbot from `universe`, memory on small servers, existing listeners, upgrade and uninstall coherence, vacuous smoke assertions).
- A second, delta-only pass by both reviewers after the workflow turned green found no blocker in the operational review and one carried-over point in the security review (links inside the clone were accepted without looking at where they lead). Applied: only plain files and directories are accepted in the clone (links are refused outright after a third look showed that checking where a link leads can be raced); fixed search path and locale from the first line; the swap file is prepared under a temporary name, validated before reuse and listed with `nofail`; the database-account marker now exists only during creation; an existing administrator is detected before a password is generated, and a lost saved password stops the run instead of being replaced; the shown-marker is written before the password is displayed; `upgrade.sh` checks the host name, the certificate files and `nginx -t` before stopping anything. Declined as optional: an exact Host check on the temporary certificate-challenge site (it serves one static directory and nothing else).
- Edge behaviour was also reproduced locally with the Ubuntu 26.04 Nginx 1.28.3 binary run unprivileged against the rendered templates.
- Not verified: a rented server, real DNS and the live Let's Encrypt service, a 1–2 GB server, interrupted runs, `upgrade.sh`, `uninstall.sh`, a machine reboot. Details are in `docs/operations/AUTO_INSTALL.md` under "Verification status".
- A public-exposure check of the repository (it was already public at the time) found no live secret in the tree or history; specifications, pricing, session logs and the owner's commit e-mail address are readable while it stays public.

## Prompt 9 (owner)

> the install was successful but when i logged in for the first time and after signed up for MFA it required i change the password but everytime i put in a password it gave me this message. I never used any other password other than the password that was generated how can it know this passwords i was setting if this is a new frehs system install

(A screenshot of the "Set a new password" page was attached. It shows the red message "Your current password is incorrect." and a "Current password" field holding a value that is not in the format of the generated temporary password. The value is not reproduced here.)

## Response and actions (prompt 9)

- Diagnosis: the portal does not know any earlier passwords. The red message concerned the first field, which must hold the temporary password from the installer; the blue advice above it ("a password you haven't used here before") was read as the error. The server only returns that message when the first field does not match the stored password (`server/modules/identity/auth.ts`, `changePassword`); the sequence bootstrap password, authenticator enrolment, password change is covered by `tests/integration/journey-admin.test.ts`.
- Likely source of the wrong value: typed there by mistake, or filled in by the browser's password manager from an entry saved for the same address.
- Fix in the portal (client only): the forced-change page now labels the field "Temporary password" with a hint, rewords the advice, reports a wrong temporary password on that field with a message that says where the new password goes, and carries the sign-in name for password managers. Test added in `client/src/features/auth/auth.test.tsx`.
- The owner was advised not to use the password visible in the screenshot, and how to read the temporary password again on the server.
- Recorded in `docs/operations/AUTO_INSTALL.md`: the owner's report of a successful installation on their own server (a report, not a recorded test).

## Response and actions (prompt 11)

- Customer ID before this change: `RP-` plus seven characters from a 32-character alphabet, drawn from the operating system's random source (never incremental). Changed to `RPCUS-` plus nine characters from 0-9 and A-Z, drawn with rejection sampling so every character is equally likely; uniqueness is enforced by the existing reservation table. Existing customers keep their ID. Test: `server/modules/identity/pure.test.ts` (run by the lead, passed).
