# HTTP, identity and assurance security review

This read-only review covers `server/trpc/**`, `server/container.ts`, `server/main.ts`, `server/core/**`, `server/db/client.ts`, `scripts/ops/migrate.ts`, and the server-side identity and assurance modules. The working snapshot was based on `2c71c18`, with concurrent assurance work in the shared checkout. File locations refer to the reviewed snapshot; all findings below are confirmed by source inspection and were sent to their respective owners for remediation. No live exploitation or timing measurement was performed.

## High severity

- **ID-01 | Password rehash can undo a credential change:** `server/modules/identity/credentials.ts:33–40` verifies an earlier hash but updates it by user ID alone if it needs a rehash. Assurance step-up calls this function before its transactional actor check (`server/modules/assurance/factors.ts:231–244`). If a reset or administrative password change commits during verification/rehashing, the stale write can restore the old password, even if session revocation later blocks step-up. This path requires a session admitted to step-up and a hash eligible for rehash. Identity should make rehash conditional on the prior hash and live local account state, fail on a credential change, and coordinate with Assurance to bind password proof to the current credential under the user lock.
- **ID-02 | Shared preview returns a live password-reset bearer:** The public reset request returns the generated redemption link for an eligible account in preview (`server/modules/identity/router.ts:66–69`, `server/modules/identity/auth.ts:50,286–324`, `server/modules/identity/tokens.ts:24–34`). Redemption updates the password and revokes active sessions (`auth.ts:328–343`). An enrolled MFA factor still protects sign-in; an already email-verified account with no enrolled factor can proceed to enrollment after the password change (`server/modules/identity/transitions.ts:23–31`). This is preview-only, but the demo route is not limited to caller-owned fixture accounts. Identity should not return live reset links to unauthenticated preview users; use isolated fixtures or an operator-only mail capture. Review preview registration and verification links separately against the chosen demo isolation rules.

## Medium severity

- **ID-03 | Reset and verification cooldown checks are not atomic:** `server/modules/identity/auth.ts:265–282,286–323` checks cooldown before transactional issuance; verification resend does not lock the user, and reset only checks that the locked row exists. Multiple admitted requests can pass the same cooldown and supersede a token that is already in the mail outbox (`server/modules/identity/tokens.ts:24–32`). Lock the user, recheck eligibility and cooldown against current state, then keep that lock through issue and enqueue. Require a currently active local account at reset redemption as well (`auth.ts:334–335`); no local-to-SSO conversion was tested.
- **ID-04 | Public recovery and registration do account-dependent work:** In `server/modules/identity/auth.ts:286–324`, unknown/ineligible reset requests write an audit event, recently issued requests take a short cooldown path, and eligible requests start a transaction and issue a token, enqueue mail and record an audit event. Registration also takes different database and outbox paths (`auth.ts:149–187`). Matching success bodies do not remove differences in work or branch-specific failures. Route public requests through the same bounded durable acceptance path, and move eligibility, cooldown, mail and account-specific audit into worker handling. The timing magnitude and detectability in any deployed environment are unmeasured.
- **ID-05 | Privilege mutations trust stale actor authority and can violate the last-admin invariant:** `server/modules/identity/admin.ts:55–73,154–188,315–356` validates the request principal but does not recheck the actor's live session and role inside the mutation. Target locking and revocation do not prevent a stale in-flight administrative write after actor revocation or demotion. The last-admin count is also an ordinary read (`server/modules/identity/users.ts:91–98`); two active administrators concurrently demoting or suspending each other can each count the other as active while updating different rows. Use deterministic actor/target locking and revalidate liveness, role, pending transitions and step-up before effects. Serialize the last-admin invariant across every writer that can reduce the active-admin set.
- **ID-06 | Session transactions can starve the connection pool:** Session creation and `assertCurrent` each load policy from the settings store inside an open transaction (`server/modules/identity/sessions.ts:62–67,120–128,193–198`). On cache miss, the settings store reads using its independent pool handle (`server/modules/platform/settingsStore.ts:88–95`). With one pool connection, the transaction waits on the same pool it occupies. With all slots occupied by such transactions, a larger pool has the same problem. Read policy before opening the transaction or use a transaction-aware settings read on the same connection. Verify cold-cache sign-in and session assertion with one pool slot.
- **C-01 | Database URI parameters can override driver hardening:** Runtime and migration connections pass the full URI to mysql2 with `multipleStatements: false` (`server/db/client.ts:15–28`, `scripts/ops/migrate.ts:19`). The installed mysql2 merges URI query options where supplied options are falsey and parses option values (`node_modules/mysql2/lib/connection_config.js:76–86,334–358`). Thus the false setting does not guarantee multi-statement SQL stays disabled; the URI can also set unexpected driver debug or TLS options. This is a deployment configuration boundary, not a remote injection claim. Parse and allowlist the DSN components, construct explicit driver options without `uri`, and adopt explicit TLS and debug policy.
- **C-02 | Migration failure can write unsafe diagnostics:** `scripts/ops/migrate.ts:13–19,31–40` opens the secret file and connects outside its catch, and forwards arbitrary `Error.message` in debug mode. The installed Drizzle query error includes SQL and parameters (`node_modules/drizzle-orm/errors.js:10–14`). Wrap the entire CLI flow, including shutdown, in a boundary that emits fixed stages and reason codes only. Report failed, partial or unknown migration outcomes explicitly when persistence cannot be established. No actual exposure of credentials in operational logs was observed.
- **C-03 | Required database TLS does not verify the server name:** `server/db/connectionOptions.ts:60–69` configures certificate-chain validation but omits `verifyIdentity`. The installed mysql2 driver opts out of the hostname check when that setting is missing (`node_modules/mysql2/lib/base/connection.js:424–468`). An operator who enables database TLS is not guaranteed that the peer's certificate names the configured host. Enable `verifyIdentity` and cover DNS and IP SAN mismatch behavior with the actual driver. No live handshake was attempted.

## Remediation status

- **C-01 and C-02, closed on source re-review:** `4cd30c3` stops passing database URIs to mysql2 and reports bounded migration diagnostics with explicit outcome language. The 11 connection option tests passed through the single-file wrapper.
- **C-03, closed on source re-review:** `d185cdf` enables mysql2 `verifyIdentity` explicitly; the connection-option tests assert it. No live MySQL TLS handshake was verified.
- **ID-01, ID-02, ID-05 and ID-06, closed on source re-review:** Identity revision `219eaa8` and the reviewed assurance code condition the rehash on the prior hash and verify step-up inside the actor transaction. Public reset always returns only `{ accepted: true }`. Identity admin mutations lock actor and target in a consistent order and assert persisted role, session and step-up status before writing. Session policy reads now use their existing transaction connection. An authenticated user retrieving their own email-verification link is an accepted preview-only exception, not a public password-reset path.
- **ID-03, partially remediated:** `219eaa8` serializes verification resend and checks eligibility under lock. The async reset worker still makes a nonlocking account peek before acquiring the user lock, then performs a nonlocking token cooldown lookup (`server/modules/identity/auth.ts:333–352`). Under MySQL's default repeatable-read policy, the early read can fix a snapshot that predates a competing issuance, even after lock handover. Use a current token read or read-committed isolation. No race reproduction was performed.
- **ID-04, partially remediated:** Public reset now enqueues identical work without looking up account eligibility. Registration still writes different database/outbox state in its two synchronous branches despite matching response bodies in standard profiles (`server/modules/identity/auth.ts:145–209`). No timing measurement was performed.

## Files follow-up

The files server review covered revision `48d7b96`, focusing on upload admission/promotion, ticket redemption and descriptor-based private storage. Existing single-file runs passed 14 files integration tests and 4 storage tests; those passes do not cover the findings below. Ticket redemption is single-use and bound to the user and session, and checks live order authorization, session and visibility before opening the descriptor. Multipart has independent envelope and file bounds and rechecks write authority before promotion. The storage adapter traverses descriptor-relative paths, constrains namespaces/leaves, and refuses unsafe file and directory types.

- **F-01 | Medium | Import file adoption can starve the pool:** `server/modules/files/index.ts:137,287–295,652–656` reads the file rules through the settings pool during a caller-owned transaction (`server/modules/portable/importWorker.ts:235–241`). A supported single-slot pool cannot satisfy a cold-cache second checkout. Pass the existing `tx` to the rules read. The import planning call is outside its SQL transaction and does not share this specific defect.
- **F-02 | Medium | Retention opens an independent audit connection while holding a transaction:** `server/modules/files/index.ts:404–416` holds a file-row lock and awaits `audit.record(input)` without a transaction handle. The audit emitter then takes a pool connection (`server/modules/audit/emitter.ts:139–153`), stalling a one-slot pool. Preserve the durable pre-unlink audit intent in a separate, already committed phase with no held connection, then reacquire and revalidate file eligibility and worker lease before deleting. Do not merely put the intent in the same transaction as the unlink.
- **F-03 | Medium | Admission settings are written using a stale principal:** `server/modules/files/index.ts:623–629` uses a pre-transaction role and step-up check for modifying allowed file formats and resource limits. A delayed request can write policy after revocation or demotion. Assert current actor/session inside the write transaction and enforce persisted step-up freshness before applying the change.

## Coverage and limits

- **Existing tests:** `scripts/dev/test.sh tests/foundation.test.ts` passed 7 tests; `scripts/dev/test.sh server/modules/assurance/assurance.test.ts` passed 17 tests. Each ran as a single-file invocation. These are baselines, not regression tests for the findings. The assurance fixture substitutes identity APIs, so these passes do not exercise the real identity/assurance credential or pool boundaries.
- **Positive checks:** Token redemption takes the user lock before its final token read, then checks purpose, expiry and consumption. Assurance binds WebAuthn ceremonies to account, session and purpose, validates expiry and origin/RP ID, and enforces user verification and applicable counters. TOTP replay and recovery-code consumption have transactional protections. HTTP/tRPC separates preview and standard transport, constrains remediation procedures, and formats safe client errors. Identity mail uses an encrypted payload, and the outbox hashes idempotency keys before persistence.
- **Follow-up verification:** No deployed browser/proxy path or reverse-proxy access-log configuration was verified. Confirm that live edge logs and analytics never capture one-time credentials in URLs. Revisit whether self-service factor removal/replacement should invalidate earlier session assurance; current code does not bind sessions to a factor credential or version. Treat these as follow-up checks, not additional confirmed findings.
