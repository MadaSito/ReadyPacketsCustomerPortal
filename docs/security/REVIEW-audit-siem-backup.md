# ReadyPackets audit, SIEM, and recovery review

This is a read-only review of peer-owned implementation. Findings state consequences verified from source; race conditions and failure modes were traced through the code, not reproduced. File and line references for the initial audit review are from `48732b0` and its ancestors. Owner notifications are not evidence of a fix.

## Audit

### High severity

- **Unauthenticated pruning marker**: `server/modules/audit/chain.ts:253–274` accepts a missing event as pruned if its tombstone matches the public event ID and digest already in the chain; `server/modules/audit/schema.ts:158–172` holds no authentication tag. A database-only writer can make unauthorized deletion indistinguishable from legitimate pruning without knowing the chain key. Authenticate each tombstone or batch receipt with a dedicated key and verify its installation, chain sequence and digest binding; write the receipt in the same transaction as the deletion.
- **Deletion precedes durable retention evidence**: `server/modules/audit/retention.ts:160–177,180–228` commits deletion per batch but records the durable outcome separately once the run finishes. An interruption or failed audit insert can leave irreversible deletion with no durable run outcome. Persist intent before starting; record receipt, progress and mandatory audit in each deletion transaction, then finalize the run independently. Coordinate hold and open-case attachment/status changes with deletion: the locking read at `retention.ts:151–169` does not lock related rows in the nested hold/case predicates; `retention.ts:105–133` and `cases.ts:188–239` do not take a common retention guard. Recompute eligibility or policy under a documented shared lock.
- **Export worker writes are not fenced**: `server/modules/audit/exports.ts:165–172,189–224,246–260` updates running/error states without a fence and checks ownership outside the publication transaction. A stale worker can mutate export state after losing its lease. Use `job.assertStillOwned(tx)` in the same transaction as each state write, couple publication to lease ownership, and clean up a losing worker's private object. Generation also uses a stored requester ID with a hard-coded admin actor rather than rechecking current eligibility; reauthorize at execution and publication, not only admission and download.

### Medium severity

- **Verification can misreport concurrent sealing or partial coverage**: `server/modules/audit/chain.ts:215–241,278–330` reads the head before paging and does not bound pages to that head. A concurrent append can change the result compared with the earlier head; suffix or truncated scans can also overwrite the full-chain status. Verify in a consistent read snapshot against a fixed head, report coverage explicitly, and do not let a partial success clear a previous full-chain failure. The normal health count excludes events below the scan watermark (`chain.ts:367–375`); separately surface older unsealed events instead of treating an empty fast-path backlog as proof of completeness.
- **Signing with an unexpected key does not fail closed**: `server/modules/audit/chain.ts:54–70,126–190,284–296,335–349` derives separate HMAC and Ed25519 material and pins verification to the local public key, but append and checkpoint paths do not validate the expected key identity before writing. A wrong replacement key can add rows incompatible with earlier history. Bind key versions to persisted chain state, reject changes before appending, and define an explicit authenticated rotation and verifier trust policy.
- **Manual signing uses a read capability**: `server/modules/audit/integrity.ts:88–100` allows manual checkpoint writes under `audit.read` and writes the audit event after the checkpoint. Use a write capability with fresh step-up, and lock the head and insert the checkpoint and its audit event atomically.
- **Attribute policy is not an allow-list**: `server/modules/audit/envelope.ts:122–135,188–207` accepts arbitrary attribute keys and scalar values that pass pattern checks, and `envelope.ts:330–333` copies all retained attributes to the external export projection. For example, `server/modules/orders/orderService.ts:716` passes prior and new order references as attributes; they are not projected using the envelope's pseudonymous resource-reference field. Use an event-specific registry with enumerated fields and types, distinguish local-only and external fields, and avoid blanket name-based exceptions for digest values.
- **Query limits do not bound all parser and DB work**: `server/modules/audit/query.ts:84–89,99–125,133–157,171–181` applies global node and nesting limits after recursive parsing and exposes JSON attribute matching. `server/modules/audit/search.ts:200–231` aggregates within a bounded date window but limits result groups rather than rows scanned. Validate depth and total nodes before recursive traversal, restrict filtering to enumerated indexed fields, and apply a database execution budget to search and aggregation. SQL values in the reviewed query builder are parameterized; this is a cost/availability finding, not a verified SQL injection.
- **Evidence export has no read snapshot or original head**: `server/modules/audit/exports.ts:135–162,190–208` pages over live records before reading the chain head for the manifest. Writes and pruning during export can make the evidence set differ from the manifest's chain state. Freeze the read boundary and keep the selection consistent; alternatively explicitly label a live export, its coverage and its limitations rather than implying a point-in-time archive.
- **Download success is premature**: `server/modules/audit/exports.ts:278–287` records the download and increments the count before opening the object; `server/modules/audit/http.ts:13–25` can subsequently fail while transferring it. Record attempted access before opening, and separately record failed, interrupted/unknown, or completed server transfer; never imply the client obtained or verified the complete object.

### Low severity

- **Different step-up semantics at the service boundary**: `server/modules/audit/access.ts:19–29` accepts a slightly future timestamp and does not reject a non-finite timestamp, unlike the common guard. Reuse the central helper to avoid divergent direct-call policy. The HTTP and tRPC layers already apply their own authentication/capability gates; no direct untrusted timestamp path was verified.

### Verified controls

- **Emitter**: `server/modules/audit/emitter.ts:139–162` awaits the insert and propagates failure from `record`, using the caller's transaction when supplied. Buffered `note` is separate and best effort, not transactional evidence. Retention and checkpoint findings concern callers not using the transaction contract.
- **Seal serialization and read authorization**: `server/modules/audit/chain.ts:137–190` locks the singleton head row before allocating chain sequence; the reviewed verifier issue is separate from sequence allocation. `server/modules/audit/router.ts` declares capability gates, and `server/modules/audit/http.ts:13–18` requires export capability before handing off to the requester-scoped download service. No customer route to the audit center or arbitrary raw SQL filter was identified in the reviewed paths.

### Audit owner follow-up

Source review of `a5cd080` confirms authenticated tombstones, transactional retention evidence and a shared guard, an upper bound on verifier pages, persisted signing key identity checks, fenced export state transitions, bounded recursive query parsing, and a fresh privileged guard for manual checkpoint creation. These checks confirm that the protections were added, not that all related races are resolved.

Open items in the updated code include partial checks overwriting full-chain health and the fast backlog count hiding older unsealed rows (`chain.ts:357–361,399–407`), generic external attributes (`envelope.ts:129–139,201–213,344–346`), JSON query work (`query.ts:156–159`), and retention during export. The export now pins a head and cutoff, but each page still performs a new inner join against live rows and the manifest can still claim `complete` after intervening pruning (`exports.ts:153–161,201–215,229–237`). Use one read snapshot or a retention pin covering the export, or qualify the manifest's completeness.

## SIEM

SIEM line references are from the runnable server handoff at `7c46d4a`. The findings below were verified by source inspection, not reproduced against a live collector.

### High severity

- **Collector identity is not bound to credentials or backlog**: `server/modules/siem/index.ts:653–666,740–785` permits changing collector authority/path/transport without clearing or explicitly reauthorizing credentials; `server/modules/siem/settings.ts:311–337` retains omitted material. The worker reads a destination and then separately loads unversioned secrets by destination ID (`index.ts:1511–1550`); a concurrent edit can combine an old endpoint with fresh credentials, or a new endpoint with cached old credentials. The test path shares this split read (`index.ts:965–968,1035–1043`). Pending rows carry `destinationVersion` (`index.ts:1432–1442`) but transmission ignores it (`index.ts:1523–1549`), so a new collector or less permissive filter can still receive an earlier revision's data. Bind secrets and queue admission to an approved endpoint/revision, demand explicit reauthorization of credentials and pending data on changes, check the revision before sending, and prevent completed probes or sends for stale revisions from overwriting current status.
- **Concurrent secret updates can undo rotation or deletion**: `server/modules/siem/settings.ts:227–240,299,349–383` reads and replaces one complete settings entry for all destinations. `server/modules/platform/settingsStore.ts:100–103,140–152,247–263` does an unlocked read and locks the row only at write time, with no compare-and-swap supplied by SIEM. Edits to different destinations can therefore overwrite each other's changes or restore a removed credential entry. Store independently encrypted per-destination credentials, or lock the shared credential entry before reading and modifying it with version checks.
- **Retention can silently stall forwarding**: `server/modules/audit/search.ts:253–266` advances the cursor over missing event rows, but `server/modules/siem/index.ts:1405–1409` stops without persisting advancement when a whole bounded page contains no remaining payloads. Newer records can be stranded indefinitely; events not yet spooled can also be pruned during extended outages despite the no-drop health message (`index.ts:1880–1893`). Persist verified progress-only pages under the lease, separate authenticated pruning from unexplained missing rows, and alert on cursor age and lost coverage rather than just queued rows. Define how retention coordinates with lagging collectors.
- **Destination lease uses an unrelated fence identity**: `server/modules/siem/index.ts:1307–1356,1752–1785,1927–1959` persists a destination-wide maximum from a fence scoped to one jobs row. An isolated retry at token 2 can prevent all new scheduled jobs at token 1 from advancing that destination. Reused owner ID across attempts of the same jobs row also lets an older attempt's `finally` clear a new attempt's destination lease. Use a destination-specific monotonic generation and a unique acquisition identity, obtain and check the lease on the DB clock, renew or bound work before expiry, and fence every mutation and network dispatch against that generation. Keep the jobs-row lease as an additional, separate guard.

### Medium severity

- **Pooled connections skip current egress authorization**: `server/modules/siem/transport.ts:326–347` returns a writable pooled socket before checking current egress policy; the old socket can outlive a policy change. `transport.ts:179–267` also falls back to its own DNS/IP rules when the integrations resolver is absent, losing central policy enforcement. Reauthorize the pinned peer for each batch, evict on policy or endpoint changes with a bounded pool lifetime, and require the central port in deployed composition; inject an explicit fake only in tests.
- **Generic scalar patterns do not enforce a privacy allow-list**: `server/modules/siem/projection.ts:26–37,57–72,89–129` accepts arbitrary counts and short scalar metadata under permitted names. These fields reach the spool (`index.ts:1417–1443`) and adapters such as OTLP (`formats.ts:191–195`). Use event-specific typed allow-lists for both counts and attributes; default-drop unclassified fields from external projections and independently test parity with export policy.
- **Retry ordering and ambiguous delivery are underspecified**: `server/modules/siem/index.ts:1523–1534` filters by retry-ready time before sorting, so newer rows can pass an earlier backed-off row. `index.ts:1590–1699` uses `retryable` but drops `uncertainAfterWrite`; retries can resend a partially accepted batch, and dead letters do not preserve ambiguity. Keep event IDs for deduplication, persist distinct attempted/uncertain outcomes, and explicitly choose either head-of-line ordering or out-of-order progress. A local TLS flush cannot guarantee receiver ingestion, and an OTLP 2xx with partial success does not establish rejection of every row. Document the guarantee accordingly and separate transport acceptance from collector acknowledgement.
- **RFC 5424 keys can collide; message-body fields are ambiguous**: `server/modules/siem/rfc5424.ts:230–245` truncates dynamic parameter names to 32 characters so different keys can become the same name in one SD element. `rfc5424.ts:249–268` appends unquoted dynamic key/value fields beside core values, allowing ambiguity for downstream parsers even though record framing is intact. Use fixed unique structured keys and a structured or quoted body without duplicate core fields. No CR/LF framing break or unescaped SD closing delimiter was identified.
- **Read capability can initiate an external credentialed test**: `server/modules/siem/index.ts:965–988,1028–1065` uses `siem.read` for a network request, including disabled destinations, and evicts the shared delivery pool to start the probe. Separate read and actively sending capabilities, require reauthorization/step-up and rate limiting, and use an isolated one-shot socket. Bind probe updates to the revision tested.

### Verified controls

- **Transport**: New connections are pinned to approved addresses, use TLS 1.2 or newer with explicit certificate-chain and hostname verification, and support custom trust anchors and optional mTLS. The HTTPS adapter refuses redirects (`server/modules/siem/transport.ts:347–375,680–720`). Collector secrets are encrypted with destination-and-slot-bound associated data in addition to the settings-store envelope (`server/modules/siem/settings.ts:243–267,349–355`); the issues above are credential lifecycle and scope, not plaintext at rest.
- **Durability and wire framing**: Projected inserts and consumer checkpoint commit together (`server/modules/siem/index.ts:1453–1483`), with a unique destination/event constraint (`server/modules/siem/schema.ts:78–106`). RFC 5424 values escape quotes, backslashes and closing brackets and neutralize line controls; RFC 5425 frames use byte lengths (`server/modules/siem/rfc5424.ts:121–157,358–362`). These controls do not resolve the coverage and retry semantics findings above.
