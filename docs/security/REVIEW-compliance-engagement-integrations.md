# Security review: Compliance, Engagement, and Integrations

This is a read-only review of application code, not a penetration test or a security certification. Findings below are based on the cited code paths; the module owners received the findings directly. Paths and line numbers refer to the initial review snapshot and may move as fixes land.

## Findings at the reviewed snapshots

The runtime review covered Compliance `e400060`, Integrations `3f99849` plus then-current working changes, and the Engagement working tree. “Verified” means the cited behavior is visible in code. It does not imply a live provider, browser, or synthetic network attack was exercised.

| ID | Severity | Evidence and impact | Remediation |

| BILL-01 | High | `server/modules/integrations/stripe.ts:175–219`; `server/modules/compliance/invoicesService.ts:1392–1431,1475–1501,1589–1616`. The adapter treats a completed Checkout Session as paid without checking payment status, uses different identifiers for Checkout and PaymentIntent events, and forwards a cumulative refund total as a new amount. The ledger deduplicates event IDs, not the underlying payment/refund, can infer an invoice from order metadata alone, and can fall back to a different payment, including a manual one, when a refund cannot be matched. Authentic provider events can therefore over-credit an invoice, mark payment prematurely, or misattribute a refund. | Keep automatic payment posting disabled until the adapter consumes only confirmed payment evidence, requires an exact local/provider binding, and deduplicates stable payment/refund identities. Record distinct successful refund amounts or reconcile cumulative totals against a high-water mark; never fall back to a different payment. Bound and reconcile provider amounts against the recorded intent. |
| INT-01 | High, feature off by default | `client/src/features/integrations/consent.tsx:152–174,246–264` and `client/src/app/App.tsx:5–13`. Clarity executes in the main app realm; purge is triggered by a passive effect after the eligibility change has rendered. The private subtree can commit before deletion/reload, and deleting a script element and global cannot remove already-installed observers. The eligibility check also uses pathname only, while the provider script can inspect the full document URL. A browser run did not confirm vendor collection. | Keep Clarity off until it is isolated to a dedicated anonymous document/realm without portal authority, or prevent private React content from rendering synchronously in a tainted document and enforce full-document navigation. Acceptance checks publication state, origin, active document and body hash, but not the actor's audience/current effective version; the authenticated caller supplies evidence method for a policy that does not require a signature. Staff-targeted policy content can be publicly returned, and the evidence label or version can misrepresent the accepted policy. | Filter public-facing policies by customer/public audience; require audience and version eligibility under transaction-safe reads. Derive acceptance methods from the actual portal, registration, or signature sequence rather than accepting a self-asserted method. |

## Fixed initial findings

- **COMP-01 (medium), COMP-02 and COMP-03 (low)**: Verified in `e400060`: character/byte limits now align with `MEDIUMTEXT` policy and ciphertext storage; policy length is rechecked after normalization; reserved intake keys are filtered, and the answer validator uses `Object.hasOwn`.
- **IPv6 transition classification**: Verified in `3f99849`: recognized mapped, compatible, translated, NAT64, 6to4 and Teredo addresses receive an unconditionally denied classification. The documentation prefix identified during review was added to the reserved range check.

## Controls reviewed and evidence limits

- **Billing**: Invoice body and ledger detail enforce parent-order read authority. Draft invoices and staff-only payment notes are excluded from the customer view. The manual payment and refund operations lock the invoice, validate currency and check remaining/refundable amounts. These checks do not make provider event reconciliation safe.
- **Engagement**: Order message reads and writes use peer object checks; writes recheck in transaction. Customer tickets are requester-scoped; staff-only messages/notes are filtered on customer list/detail/search paths examined. Dedicated notifications avoid including message and ticket content. Trusted `notify` callers must still pass safe titles/links. No stress test or production SQL execution plan was collected.
- **Integrations**: HTTPS rejects redirects rather than following them, applies size bounds, classifies all returned addresses, and requires TLS 1.2+ and certificate verification. SMTP is handed a numeric pinned address, preserves SNI, requires STARTTLS or implicit TLS, and validates envelope recipients and subject control characters. Provider secrets inspected are stored via platform secret definitions; configuration views report secret presence rather than returning SMTP/Stripe secret values. The separately exposed analytics IDs are public project identifiers, not provider credentials. No external DNS, live TLS, SMTP or Stripe transactions, or browser capture were exercised.
