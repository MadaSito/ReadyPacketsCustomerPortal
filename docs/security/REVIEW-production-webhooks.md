Findings below are verified by source inspection unless explicitly labeled a deployment dependency.

## Remediation re-review

Reviewed `645e42a` and the PW-02 follow-up `347955f` with its Jobs dependency `ec3dbd3`. **PW-01 through PW-08 are closed in the reviewed source.** Keep live delivery disabled until the deployment dependencies below are verified.

- **PW-02 | Closed in `347955f` with `ec3dbd3`:** The intermediary `645e42a` filtered after the row limit, judged staleness without the job ledger, and allowed an old finalizer to overwrite the reconciled state. The follow-up binds the delivery job in the original outbox transaction, filters age and expiry in SQL before the limit, and locks the job ledger before the outbox (`production/service.ts:522–641,652–837,1021–1056`). Reconciliation leaves live leases and unexpired queued jobs alone, settles expired leases without replay, and rolls back if the dispatch changed. The worker finalizer requires matching state, version, attempt, fencing token, and job ID (`production/service.ts:1560–1594`). Recovery clears ciphertext and records `unknown` for a possibly delivered attempt. `unknown` cannot authorize P201 and triggers a verify-downstream warning before an admin resend. Cleanup needs a working database, durable audit, and reconciliation worker; the expiry is not a promise of immediate scrubbing while these are unavailable.
- **PW-01 and PW-07 | Closed:** Delivery reads only receiver status, and persists a summary derived from controlled server reason codes; the production response cap is now 8 KiB. Resend persists only the server-classified reason, and the settings audit replaces the auth header name with a Boolean configuration flag.
- **PW-03 and PW-04 | Closed:** The worker verifies order survival, lock and cancellation state, current owner and active account, and live P101 packet scope before the send. It compares the queue-time keyed destination/auth fingerprint to the live values, including changes made via generic Platform settings. These pre-send checks cannot retract a request already in flight.
- **PW-05, PW-06, and PW-08 | Closed:** The start/resend transactions take the order lock before persisted actor authorization; missing Identity now fails closed, and step-up age uses a post-lock clock. Omitted P101 `release_status` now defaults to the empty string.
- **Platform export exclusion | Verified:** The three production secret definitions explicitly set `exportable: false`. The production server test verifies exclusion with generic encrypted secret export requested and rejects import of those keys.
- **Independent final single-file retest:** `server/modules/integrations/production/production.test.ts` (15 passed), `server/modules/integrations/production/payload.test.ts` (8), `server/modules/integrations/integrations.test.ts` (10), `server/modules/jobs/jobs.test.ts` (26), and `client/src/features/integrations/production/production.test.tsx` (7), each via `scripts/dev/test.sh`, for 66 passing tests. `scripts/dev/tc.sh` and scoped `scripts/dev/lint.sh` also passed. ## Findings

### High

- **PW-01 | Provider response text can expose secrets and client PII to staff:** `production/service.ts:231–246,255–278,870–904,946–957,1929–1942` only strips control characters and truncates provider response text. It persists that text and serves it to order-history viewers, including staff whose payload preview deliberately masks PII. A permitted endpoint can echo a credential, full URL, client name, or client email. Keep only the HTTP status and a fixed local reason code; never persist or show the receiver's body.
- **PW-02 | Interrupted dispatches can retain payloads past the retry window and block the phase:** `production/service.ts:669–671,800–831,1729–1748` records `sending` before I/O, but there is no reconciliation path when a worker fails before finalization. The job queue reaps the job without rerunning this `retrySafe: false` handler (`jobs/queue.ts:298–312,347–369`); the outbox row stays `sending`, the encrypted PII remains, and resend refuses the row. An interruption after retry state is committed can similarly leave `queued` without a runnable job. Reconcile against the job ledger or expire with a fenced, audited transition that clears payload data and preserves uncertainty. Do not automatically replay possibly delivered requests.

### Medium

- **PW-03 | Delivery does not recheck order release eligibility:** The worker loads dispatch and settings and validates the encrypted bytes, but does not reload Orders before sending (`production/service.ts:649–818,834–868`). Request-time checks therefore do not stop a queued or retried P101 after the order is placed on legal hold, finalized, transferred, or otherwise becomes ineligible. Recheck current order existence, allowed lock state, and the owner against the queue-time binding before publishing the payload. A worker cannot retract a send already in flight.
- **PW-04 | Queued payloads can move to a different receiver after settings change:** The worker resolves the phase URL and auth from current settings on every attempt (`production/service.ts:675–680,859–868`). Changing a secret URL to another allowlisted destination can send already-enqueued data there. Retrying the same key at a different receiver also does not establish deduplication. Bind the dispatch to the authorized phase destination/configuration without exposing secrets, and refuse or reconcile on an incompatible change. The generic Platform settings routes are an additional write path (`platform/router.ts:40–67`); a binding must not depend solely on the dedicated integration settings mutation.
- **PW-05 | Dispatch mutations take actor locks before the order lock:** Queueing P101/P201 and resending lock identity first (`production/service.ts:1453–1458,1570–1574,1724–1728`), while Orders mutations use order → actor. This reverses two lock acquisitions for the same order/actor pair. Take the order-only lock before checking persisted actor authority. No deadlock was reproduced.
- **PW-06 | Transactional authorization fails open if the Identity API is absent:** The settings, trigger, and resend helpers condition their authoritative check on `assertCurrent` being present (`integrations/authz.ts:45–67,90–103,135–157`). Normal container construction supplies Identity, but a missing dependency silently falls back to stale request state. Refuse if Identity cannot verify the actor, and compute persisted step-up age after waiting for its locks.
- **PW-07 | Unrestricted resend prose can enter shared audit and history:** `production/service.ts:593–595,1716–1719,255–278` persists and returns the operator's free-text reason and copies it to audit. Character checks and generic secret-pattern detection cannot exclude names and arbitrary credentials. Prefer a controlled reason code or keep only a safe classification in audit and dispatch projections. Omit the configured auth header name from the settings-change event as well (`production/service.ts:1265`); the dedicated settings view only needs it if approved as displayable configuration.

### Low

- **PW-08 | `release_status` defaults to a workflow status instead of an empty string:** `production/service.ts:447–448` substitutes `scope.statusKey` when the operator supplies no label. Section D requires an empty default; preserve a valid explicit label unchanged after normalization.

## Verified controls and limits

- **Egress and dry-run:** Both production paths require HTTPS, a matching enabled `webhook` rule, and public-only address answers. `egress.ts:828–850` passes the pin from the same evaluation to the HTTPS requester, whose pinned lookup, TLS verification, redirect refusal, deadline, and 64 KiB production response cap are enforced on the reviewed default path. The dry-run calls policy resolution without making HTTP requests and does not project the normalized URL.
- **Authorization and order scope:** All nine routes have staff/admin session guards; `settings.update` and `settings.test` require `integrations.manage` and step-up, and resend requires admin plus persisted step-up when Identity is present. The staff routes use the production-trigger capability and authorize the requested order through Orders before loading its scoped dispatch rows. Staff name/email previews are masked. The tested denial fixtures are not a live deployed identity/proxy test.
- **Payload and retries:** P101 uses exact fields and string values, canonical manifest ordering, 1–6/tier consistency, and refuses missing, mixed/non-packet, or contradictory scope. Neither payload sends `order_scope_mode`. P201 takes three fields from an explicitly delivered P101 row for the same order, not from mutable account data, and requires an artifact attestation. The outbox encrypts payload bytes and verifies their hash and schema before sending. The code retries network errors, 5xx, and 429 up to a fixed attempt cap and sends a stable key for an automatic retry of one dispatch; ordinary 4xx and redirects are terminal.
- **Secrets and authorization boundary:** Dedicated settings and dry-run projections do not return plaintext secret values or the full URL. Generic Platform export filters on `exportable`, even when encrypted secret export is requested (`platform/configTransfer.ts:151–165`). `defineSecret` defaults to `exportable: false` (`platform/settingsRegistry.ts:124–147`), and the P101 URL, P201 URL, and auth value definitions do not opt in (`integrations/settings.ts:426–461`), so all three are excluded. This matches the integrator's explicit no-opt-in instruction.
- **Deployment dependencies:** Only the receiver can prove deduplication after a timeout or lost response. `Idempotency-Key` alone is not such evidence. Receiver idempotency across the full automatic retry window, live TLS validation, and a synthetic P101 → artifact verification → P201 run on the intended receiver remain unverified. A successful transport response is not proof the Phase I artifacts exist.
- **Independent single-file test runs:** `server/modules/integrations/production/payload.test.ts` (8 passed), `server/modules/integrations/production/production.test.ts` (8 passed), and `server/modules/integrations/integrations.test.ts` (10 passed), each through `scripts/dev/test.sh`. These passed on the initial review and do not close the findings above. No browser, live destination, builds or migrations were used.
