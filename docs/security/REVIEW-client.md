# ReadyPackets client review

Read-only review of the shared development checkout on November 20, 2026, including in-flight dashboard source. Primary scope: `client/src/app`, `client/src/lib`, shared UI, auth and dashboard; targeted spot checks covered available Files, Assurance, Jobs and Portable screens and their server entry points. Findings distinguish source-confirmed behavior from checks requiring rendered browser or assistive-technology testing.

## Verified security and privacy findings

| ID | Severity | Evidence and impact | Recommended fix |
| --- | --- | --- | --- |
| C-01 | Medium | `client/src/features/auth/pages/MfaEnrolPage.tsx:22–33,77–101` uses a retained TanStack mutation for enrollment setup. The response contains the raw TOTP seed, its `otpauth` URI, and the encoded QR image (`server/modules/assurance/factors.ts:127–141`). The credential stays in the shared mutation cache after confirmation or route unmount until cache disposal; completion on the same screen does not clear it either. This is unintended in-memory credential retention, not browser storage or a demonstrated remote disclosure. | Invoke `AuthApi` directly, keep only necessary setup material in component-local state, disregard late results after session change, and clear the state on success and exit. Assert a synthetic seed never enters the mutation cache. |
| C-02 | Medium | `client/src/app/providers.tsx:9–16,22–24` uses one QueryClient per application. In cookie mode `sessionTransport.ts:67–77` never emits the session change event; a definitive `identity.me` failure only hides the session view (`lib/session.ts:29–41`) and normal sign-in refreshes only `identity.me` (`features/auth/useAuthNavigation.ts:8–19`). Other feature query keys are not scoped per user, and previous data can be reused when another same-role user reaches a recently loaded screen in the same tab. Preview cleanup also keeps every key beginning with `"rp"` because it compares only the first key item, including private assurance state (`features/dashboard/components/RequiredActions.tsx:38–41`); it does not clear mutations. Explicit successful sign-out does clear the QueryClient. This is a client-side isolation issue, not a server-side authorization bypass. | Gate private screens on resolved session authority, then isolate query/mutation caches per identity and authority epoch. Cancel and purge private queries and mutations on confirmed sign-out, revocation or account/authority changes in both profiles; retain only explicitly allowlisted public queries. Test same-role account replacement and the signed-out transition with seeded synthetic private data. |
| C-03 | Low | `client/src/lib/signOut.ts:24–30` clears local cache and redirects even when remote sign-out rejects. A failed request cannot remove a live HttpOnly cookie, and preview credentials are changed only by accepted transport responses (`client/src/lib/sessionTransport.ts:67–77`). A subsequent session read can reopen the private shell even though the user tried to sign out. | Distinguish confirmed revocation from network failure and keep local private rendering locked until retry or explicit reauthentication; clear preview credentials locally on sign-out. Add a rejected-logout test in both profiles. |
| C-04 | Low, preview-only | `server/modules/identity/auth.ts:172–182,186–208` omits `previewLink` for an existing registration but returns it for a new one in preview. `client/src/features/auth/pages/RegisterPage.tsx:51–58` renders that distinction, despite the generic message. This leaks account existence within the synthetic preview installation only; the standard profile does not return that field. | Keep public registration responses uniform in preview too. If a demo requires a verification link, expose it only to a demo operator or via an authenticated self-service resend flow. Assert equivalent responses for new and existing addresses in both profiles. |

## Verified usability and accessibility findings

| ID | Severity | Evidence and impact | Recommended fix |
| --- | --- | --- | --- |
| C-05 | Low, preview-only | `client/src/app/AppRouter.tsx:140–143` uses Wouter’s hash location with default browser search. The installed Wouter hash adapter serializes native links with the query inside the fragment, but intercepted navigation moves the query to document search and leaves existing search untouched if the next target has none (`node_modules/wouter/src/use-hash-location.js:20–35,54`). `features/auth/components/bits.tsx:115–126` reads the default search hook. Copied/opened-in-a-new-tab preview links with queries can therefore fail route matching and token extraction even if a regular in-app click works. | Use paired preview pathname/search hooks that consistently parse and write the same representation, clear old params when appropriate, and exercise copied links and normal clicks independently. Keep one-time token removal in the canonical router location. |
| C-06 | Low | `client/src/ui/Overlay.tsx:140–175` vertically centers `ConfirmDialog` without a viewport max-height or an internal scroll region. Tall confirmation content or increased text size in a short viewport can place text or controls beyond a reachable edge. Standard `Dialog` and `Drawer` already have scrollable bodies. | Bound the content to the dynamic viewport and use a scrollable body with persistent accessible actions, following the standard dialog. Verify text zoom, 320 CSS px reflow, keyboard traversal and short landscape height. |
| C-07 | Low | `client/src/ui/Toast.tsx:71–86` cancels the timer on focus but does not handle focus leaving. Mouse leave also restarts the timer without checking whether the dismiss button is still focused; expiry can remove the focused element. | Track pointer and focus-within independently, resume only after both leave, and ensure removal does not strand focus. Exercise combinations with a fake timer. |
| C-08 | Low | The optional sort buttons in `client/src/ui/DataTable.tsx:75–94` are only in the desktop table. The mobile card view at lines 124–141 contains no equivalent controls. This is a shared-component behavior gap when sorting is enabled, not a claim that every shipped table uses sorting. | Include an accessible small-screen sort control driven by the same state and allowed sort keys. If desktop overflow remains possible on a data-heavy table, make the overflow container keyboard-operable and visibly focusable. |

## Authority and transport checks

- **Reviewed routes:** Auth state is server-backed (`identity.me`, `server/modules/identity/router.ts:91–101`). Public sign-in, registration, password reset, verification and activation are intentional public entry points with server input validation and credential or bearer-proof checks; origin/CSRF cover unsafe HTTP methods. MFA procedures are session-gated at `server/modules/assurance/router.ts:9–38`, with transition/step-up eligibility in the service, including `factors.ts:117–145`. Dashboard pages use `identity.me` and `assurance.getState`; console widgets are optional and must keep independent server guards. Available Files, Jobs, Portable and Assurance procedure spot checks found server guards rather than reliance on navigation visibility alone. No reviewed live procedure lacked a traceable guard; incomplete feature stubs are not covered by that conclusion.
- **CSRF and session transport:** `client/src/lib/trpc.ts:39–42` delegates to `sessionFetch`, and spot-checked raw Files and Portable calls also use it. The wrapper checks the API destination, strips caller-provided session/CSRF headers, bootstraps CSRF for unsafe methods, disallows fetch redirects, and selects preview header credentials or standard same-origin cookies (`client/src/lib/sessionTransport.ts:83–128`). Server CSRF middleware checks ordinary canonical origin and validates session-bound or anonymous CSRF (`server/http/app.ts:243–256`).
- **Sinks and persistence:** No use of raw HTML insertion, user-supplied external navigable URL, or external open redirect was identified in the reviewed paths. `safeNextPath` rejects non-local forms and history navigation is same-origin or hash-local. The setup QR is produced by the server’s QR encoder and used as an image source, not an arbitrary link. No app registration of a service worker or Cache Storage population was found in the snapshot; authenticated HTTP responses receive `no-store` (`server/http/app.ts:228–239`). Any future PWA worker should positively allowlist build-static assets and must not cache API responses, credentials, authenticated navigations, or private data.

## Verification limits

- **Automated:** Each existing single-file suite was run with `scripts/dev/test.sh`: auth (22), route guard (7), contrast tokens (88), shared UI (12) and dashboard (5). All 134 tests passed. These suites do not cover the defects above unless a dedicated regression is added; jsdom and axe are not substitutes for real layout and screen-reader validation.
- **Manual follow-up:** Verify 320–375 CSS px and 200% zoom, short viewport dialogs, keyboard-only overflow and focus targets, and announcements with assistive technology. Shared controls generally use 44 px targets, while compact links and some controls rely on spacing or labels; target geometry was not measured. Native table captions and scoped column headers, mobile labelled cards, reduced-motion CSS, and persistent toast/route live regions were present. The sticky/fixed shells need focus-obscuration testing around `RouteFocus.tsx:37–45`, skip navigation and mobile drawers. Token tests check declared pairs; also inspect the global focus color on elevated navy surfaces in rendered context, since the light focus/elevated navy token pair computes to 2.42:1 but the actual outline can be adjacent to a different background.
