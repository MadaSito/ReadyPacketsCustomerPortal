# Increment 04 security review

The ledger records defensive design and implementation findings against Increment 04 §4. Code review or an owner-reported fix is not the same as independent runtime verification. Findings stay open until the owner supplies the disposition and the relevant regression evidence; missing wiring or live evidence is identified separately. Use severity `High`, `Medium`, `Low`, or `Informational` and statuses `Open`, `Fixed, pending verification`, `Verified`, or `Accepted by lead`.

## Packages C, D, J (assurance review)

| ID | Severity | Status | Evidence and required disposition |
| --- | --- | --- | --- |
| C-01 | Medium | Open | The `recoverySignals()` guard in `server/modules/protection/request.ts` checks navigation, sign-in, step-up and protection configuration, but does not model the full local-MFA recovery chain, including the login transition and proof request. A policy that passes the check can block a later local operator sign-in. Validate recovery against the relevant bootstrap, session, local MFA route/procedures, resource requests and tRPC path shapes, or preserve a clearly scoped recovery lane subject to normal authentication and rate limits. Keep the host bypass and test it. |
| C-02 | Medium | Open | `server/modules/protection/geo.ts` trusts the configured country header from a trusted direct peer; that trusts the proxy's header contract, not the original client. Bundled proxy templates overwrite standard forwarding fields but do not grant provenance to arbitrary custom country headers. Keep header lookup disabled for stock profiles unless the edge strips and rewrites it from verified country data; document the distinction from offline MMDB and test untrusted input. This matters to both C and D. |
| D-01 | High | Open | `server/modules/identity/sessions.ts` uses a 10,000-row selection cap for all-customer and per-user revocations. A successful bulk action can leave eligible sessions active, including the host/password recovery path that relies on per-user revocation. Revoke the entire eligible set, or make bounded continuation explicit and do not report complete while live targets remain. Preserve the acting admin's session, exclude noncustomer principals from the maintenance action and test beyond the batch boundary. |
| D-02 | Medium | Open | The selection and conditional update in `endRows()` are not coupled to emitted per-session events: `revokeAny()` returns success based on selected rows, and a concurrent revocation can reduce affected count but leave duplicate `forced_end`/expiry records. Lock or condition each authoritative transition, emit only events for rows actually changed and assert idempotence under concurrent requests. |
| D-03 | Medium | Open | `sessions.timing()` in `server/modules/identity/sessions.ts` calls `policy(opts.tx)` without the current persisted role, unlike the resolver. Consequently the warning/extension UX fed by `identity.me` can use fallback timeouts after a role-specific restriction shortened the session. Derive both timing and enforcement from the same persisted role and effective expiry; test idle and absolute limits for customer, staff and admin. |
| D-04 | Low | Open | The restrictions update simulates the candidate as enabled even when the operator is disabling it. This makes a simple break-glass correction fail from a newly denied network until the operator also edits existing rules. Test self-lockout with the candidate's actual enabled state and still warn in the UI about a policy that would deny the operator if re-enabled. |
| J-01 | High | Open | `client/src/lib/consent.ts` initially missed both expiry and cross-tab invalidation. Storage/visibility listeners are now present, but the timer refresh recomputes and loses the previously published opt-in before it compares state, so unmount/cleanup can be skipped; the expired end can also re-arm repeatedly. Preserve the published opt-in until notifying the actual expiry transition, then stop re-arming. Deny locally on withdrawal, propagate changes across tabs and terminate/reload a tainted realm. Test clock crossing with an active vendor subscriber and withdrawal with a failed ledger call. |
| J-02 | Medium | Fixed, pending verification | A caller-supplied `consentId` was accepted as a grouping key. The updated server only reuses an ID inside a signed receipt and compares its MAC in constant time. User history is still selected by server-derived session identity. Verify a tampered or bare ID cannot attach to another browser receipt and document metadata/IP HMAC retention and export authorization. |
| J-03 | High | Open | Consent's local denial-first behavior must revoke only what was previously granted when a single save both removes and adds categories. Applying the entire requested choice before the ledger acknowledges it can enable a newly granted category on a failed save. Apply the intersection of current and requested grants synchronously, then add new grants only after the confirmed ledger update. Test switching categories with a rejected or stale-version response. |

### Verification required at integration

- **C**: The inspected code defaults to detection, uses bounded literal matchers and proxy-normalized IPs, bounds request-event writes by slots, encrypts event addresses, and emits stable audit labels rather than raw headers, bodies, or query strings. Verify effective API authorization, default versus tuned rate limits, break-glass reset, runtime cleanup after upgraded deployment and operator documentation. Confirm MMDB absence and malformed/forwarded country input do not silently gain trust.
- **D**: Source review confirmed fresh persisted step-up for the `sessions.revoke_any` capability through `authorizeInTx`, own-session exclusion for other-session actions, and customer-only maintenance targeting. Full integration verification remains open for parallel local and Entra sign-in under the same user/policy, per-request network change, configured unknown-country behavior, scheduled customer maintenance and cross-session revocation. Use simulated identities only.
- **J**: Client/provider cutover and real-browser integration remain unverified. Verify off/default with no optional storage or vendor requests; equal prominence for reject; GPC/DNT defaults; separate analytics and replay categories; withdrawal/expiry/version change; actual vendor scope restricted to anonymous exact `/privacy` and `/terms` without query or fragment; and no optional capture on other public pages, notably `/accessibility`. Check that real page/browser CSP, modal interactions, and user/anonymous ledger scopes agree.
